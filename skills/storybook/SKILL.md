Read the approved structured script, shared creative-direction Markdown, script plan, and target duration. Return the complete storybook using `../../schemas/storybook.schema.json`. Write scene and production instructions in English. Preserve `voiceover.text` verbatim in its original language, and keep on-screen text in the script's language unless shared creative direction specifies otherwise. Preserve IDs and asset paths exactly.

When narration includes inline motion annotations (`*italic*`, `**bold**`, inline backticks, `~~strikethrough~~`, or `%%comments%%`), read [obscript-parse-script](../obscript-parse-script/SKILL.md) and apply its element effects and approximate word timing while planning scenes. Preserve the exact approved narration, including annotation delimiters, and encode cues in the existing animation.emphasis and render_brief fields.

The supplied shared creative-direction file is the single source of truth for the basic visual standards across all videos. Follow every filled field and restriction. Blank fields and suggested field descriptions are unspecified. Set only the execution details needed by each scene; do not invent a replacement identity, imitate the source video's identity, or create or edit a creative-direction file. The approved script supplies the video's thesis and narrative context.

Each scene belongs to exactly one script_section_id and contains an exact contiguous excerpt of that section's narration. Preserve punctuation and every word. Whitespace may vary. In script section order, concatenating the scene excerpts with whitespace must equal each section's entire narration. Cover every section exactly once in order, with no omissions, additions, duplication, or interleaving. Never reconstruct narration from script.md or rewrite it for timing.

Use IDs scene-001, scene-002, ... and order 1, 2, ... without gaps. Begin at zero, make adjacent estimated timing boundaries identical, and end exactly at target_duration_seconds. voiceover.estimated_seconds equals the scene's timing interval. Prefer scenes of 3–12 seconds, allowing exceptions for natural narration boundaries; distribute time according to narration density.

Production creates silent animations. A human reads the script and handles all audio separately. voiceover.text is the exact reference passage for that human, not a TTS request. Scene intervals become the animation timeline and script recording cues. Specify no audio assets, TTS, music, sound effects, or automatic subtitles; on-screen labels remain supporting visuals.

Give each scene one principal visual idea. Describe what appears and how it moves; do not re-explain the narration, justify the visuals, or repeat the lesson. Keep required `narrative_beat` and `visual_goal` metadata to short phrases. Use `composition` for positions, scale, layering, and connectors; `visual_elements` for concrete objects and their visible roles; and `animation` for timed actions on those objects. Specify "Hard cut" for a hard cut or "None" for inactive behaviors. The last `transition_out` is "None".

The readable storybook displays `render_brief` as the scene's Layout description. Write it as a concise, self-contained English paragraph of imperative production directions. Include the visible elements and asset references, their positions and relationships, exact on-screen labels, background treatment, and the animation sequence from entrance to exit. Give scene-local seconds or relative timing such as "halfway through the scene" for changes of focus, fades, loops, and camera moves. Describe movement direction and what the camera follows. Include the transition to the next scene within the allocated interval. Prefer concrete actions such as "fade in over 0.4 seconds" to vague requests such as "add a nice animation". Include only actions useful to this scene; a static shot needs no decorative motion.

Use supplied asset paths when available and name them consistently across `visual_elements`, `asset_requirements`, and `render_brief`. Do not claim a file exists if no input identifies it. For an asset that still needs sourcing or creation, describe it concretely in `asset_requirements` and refer to it by the same name in the directions. All visible elements, text, motion cues, and required assets in the structured fields must agree with the paragraph; the renderer should not have to invent missing scene decisions.

Prefer existing SVG icons, illustrations, technical symbols, emojis, raster backgrounds, and textures from `/home/zalmo/documents/obsidian/Videos/Videos/Globals/assets` wherever they fit the scene and shared direction. The library includes general-purpose icon collections, `tech-icons`, `tech2-icons`, `tech3-icons`, `emojis-svg`, and `background1`. Plan explanations and interactions around these assets instead of requesting newly invented SVGs, hand-drawn abstract substitutes, generated images, or external stock when a library asset is suitable. Discover and inspect candidates read-only; record verified source paths consistently in the scene fields. If a specific file cannot be verified, describe the desired library asset and leave filename resolution to production rather than inventing a path. Specify palette-appropriate recoloring for monochrome foreground icons and purposeful animation of icons, SVG parts, or emoji interactions when useful. Preserve explicitly supplied assets and meaningful brand or emoji colors.

Use a custom raster image from `assets/background1` as a visible scene background in at least `ceil(total scene count / 5)` scenes, with a minimum of one background-image scene whenever the storybook has scenes. Distribute these scenes through the timeline instead of clustering them. A background counts toward this minimum only when the raster asset replaces the plain base as the full-frame background or occupies a substantial background region; a tiny icon, corner accent, or nearly invisible overlay does not count. Name the verified file path in `visual_elements`, `asset_requirements`, and `render_brief`, and give production an explicit placement treatment. More scenes may use custom backgrounds when they support the composition.

For raster background assets, inspect intrinsic dimensions, aspect ratio, and visible content relative to the output canvas. Use sufficiently resolved images as full-frame backgrounds with aspect-preserving cropping; treat tiny raster assets as likely texture tiles or substantial patterned regions instead of enlarging them across the screen. Specify repetition and tile scale, or placement across a large panel or masked region, in `composition` and `render_brief`. Check whether repeated edges form a usable pattern. Raster backgrounds and textures may be rotated, tilted, offset, cropped, or layered to build the composition; specify coverage beyond the frame before clipping transformed layers so no unintended gaps appear. Keep foreground text and icons legible. If dimensions cannot be verified during planning, state that production must inspect them before resolving scale and repetition.

Never generate, hand-author, request, or use an SVG as a scene background, even when an SVG file exists inside a background collection. Do not describe CSS-drawn or inline-SVG background substitutes. SVG icons and illustrations remain allowed as foreground elements. Before returning the storybook, count the qualifying raster-background scenes and confirm internally that the minimum above is met.
